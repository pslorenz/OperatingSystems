## Why this chapter exists

The workshop introduced PowerShell as "the shell on Windows." That is the surface answer. The deeper answer is that PowerShell is a complete object-oriented automation framework that happens to also serve as a shell. The skills you build here are the same skills that scale to writing real automation, reading other people's scripts, and (for security pros) recognizing what attacker scripts are doing.

Most beginners use PowerShell as a slightly different bash. That works for the first month and then breaks. This chapter shifts the mental model: PowerShell is its own thing, with its own conventions, and the conventions reward learning them.

## The PowerShell prompt revisited

The default PowerShell prompt shows your current location:

```
PS C:\Users\student>
```

That is generated by a function called `prompt`. PowerShell calls this function before each command and displays the return value. To see the default:

```
Get-Command prompt | Select-Object -ExpandProperty Definition
```

You see the few lines that produce the default prompt. You can replace the function with your own. We do that in the profile section below.

### The pipeline, revisited

The workshop introduced the pipeline. Worth a deeper look at one fact: in PowerShell, the pipeline is processed in chunks, not all at once.

```
Get-ChildItem C:\Windows -Recurse | Where-Object Length -gt 1MB | Select-Object -First 5
```

That command does not enumerate the entire `C:\Windows` tree, hold it in memory, then filter. It streams: as `Get-ChildItem` yields each file, that file flows through `Where-Object`, and as soon as `Select-Object` has 5 matches, it stops the pipeline. This is why pipelines on huge directories or huge result sets can still be fast.

The implication: prefer pipeline-friendly composition over building large intermediate variables. `Get-Process | Where-Object {...}` is better than `$procs = Get-Process; $filtered = $procs | Where-Object {...}`.

### Variables and the `$` sigil

PowerShell variables are introduced with `$`:

```
$Name = "Steven"
$Procs = Get-Process
$Date = Get-Date
```

Unlike bash, the `$` is part of the variable. There is no "set without dollar, use with dollar" distinction. Everywhere a variable appears, it has the dollar sign.

Variables are typed but the typing is dynamic by default. The variable's type is whatever value you assign to it. To force a type:

```
[int]$Count = 5
[string]$Greeting = "Hello"
[datetime]$When = Get-Date
```

The bracket syntax is .NET type casting. PowerShell uses .NET types throughout, which is why you can do things like:

```
$Now = Get-Date
$Now.AddDays(7)
$Now.Year
$Now | Get-Member
```

Every value has methods and properties. `Get-Member` shows you what is available. This is the pattern that distinguishes PowerShell from text-based shells: every value is an object, so every value has structure you can query.

## The help system in depth

The workshop showed you `Get-Help`. There is more.

```
Get-Help                                # general help
Get-Help Get-Process                    # the basic help
Get-Help Get-Process -Detailed          # more detail
Get-Help Get-Process -Full              # everything
Get-Help Get-Process -Examples          # just the examples
Get-Help Get-Process -Online            # opens MS Learn in a browser
Get-Help Get-Process -ShowWindow        # opens help in a separate window
```

`-ShowWindow` is genuinely useful for studying a command. It opens a separate window with the full help, which you can leave open while typing in the main shell.

The help system is not always loaded by default. To download the latest help:

```
Update-Help -Force
```

(Run this from elevated PowerShell. It needs internet access and admin rights.)

If you see "the help for the command Get-X is missing," you have not run Update-Help. Run it once and the help is cached for offline use.

### Reading parameter help

A command's help shows its parameters. Each parameter has metadata: required or optional, position, type, whether it accepts pipeline input.

```
Get-Help Get-Process -Parameter Name
```

That shows the help for just the `-Name` parameter of `Get-Process`. The "Accept pipeline input" line tells you whether you can pipe values directly to that parameter, which is a useful pattern for chaining.

### About topics

PowerShell has conceptual help under "about" topics:

```
Get-Help about_*
Get-Help about_Variables
Get-Help about_Pipelines
Get-Help about_Operators
Get-Help about_Comparison_Operators
```

The about topics are essentially mini-documentation. If you do not understand how something in the language works, there is probably an about topic that explains it.

## Profiles: PowerShell's bashrc equivalent

PowerShell has profiles. *A profile is a PowerShell script that runs automatically when PowerShell starts. It is the equivalent of bash's `.bashrc`.*

There are actually four possible profile locations, but for daily work you only need one:

```
$PROFILE
```

That returns the path to your current user profile, typically `C:\Users\<you>\Documents\PowerShell\Microsoft.PowerShell_profile.ps1` or `C:\Users\<you>\Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1` (the path differs between Windows PowerShell 5.1 and PowerShell 7).

The file does not exist by default. Create it:

```
if (-not (Test-Path $PROFILE)) {
    New-Item -ItemType File -Path $PROFILE -Force
}
notepad $PROFILE
```

Add things to the file. After saving, either restart PowerShell or dot-source the profile to load it now:

```
. $PROFILE
```

The dot followed by space is the dot-sourcing syntax. It runs the script in the current scope, so functions and variables it defines stick around in your current session.

### Things worth putting in your profile

A practical starter profile:

```powershell
# Custom prompt with the time and current path
function prompt {
    $time = (Get-Date).ToString('HH:mm')
    Write-Host "[$time] " -NoNewline -ForegroundColor Yellow
    Write-Host (Get-Location) -NoNewline -ForegroundColor Cyan
    return "`nPS> "
}

# Useful aliases
Set-Alias -Name ll -Value Get-ChildItem
Set-Alias -Name grep -Value Select-String

# Encourage finding things
function Find-Cmd { param($Pattern) Get-Command "*$Pattern*" }
Set-Alias -Name fc -Value Find-Cmd

# History config: keep more, in this session and on disk
$MaximumHistoryCount = 10000
Set-PSReadlineOption -HistorySaveStyle SaveIncrementally
```

After saving, restart PowerShell. Your prompt looks different. `ll` works as `Get-ChildItem`. `grep` works as `Select-String`. `fc service` finds every command with "service" in its name.

### Notes on profile portability

Two things to watch for:

**The profile path differs between PowerShell versions.** Windows PowerShell 5.1 looks at `WindowsPowerShell\Microsoft.PowerShell_profile.ps1`; PowerShell 7+ looks at `PowerShell\Microsoft.PowerShell_profile.ps1`. If you switch between versions, you may want both files (with shared content sourced from a third file) or symlinks.

**Profiles run with the calling user's privileges.** A profile that does something elevated (registry writes, service changes) will fail when the user is not elevated. Test your profile in a non-elevated PowerShell to make sure it does not assume admin rights.

## PSReadLine: the line editor

Modern PowerShell uses PSReadLine to handle command-line input. It provides history search, tab completion, syntax highlighting, and many other features.

```
Get-Module PSReadLine
```

That confirms PSReadLine is loaded.

Useful keystrokes (Windows defaults):

| Keys | Action |
|------|--------|
| Up/Down | Walk through history |
| Ctrl+R | Reverse search history (like bash) |
| Tab | Complete command, parameter, or path |
| Ctrl+Space | Show all completions in a menu |
| F7 | Show command history in a list |
| Alt+Up / Alt+Down | History per-character search (type a few chars, then Alt+Up to find a matching past command) |
| Ctrl+A | Beginning of line |
| Ctrl+E | End of line |

The history-list view (F7) is a feature genuinely worth knowing. Hit F7, see your last commands, arrow to one, Enter to run it.

### History across sessions

PSReadLine writes your history to a file:

```
(Get-PSReadLineOption).HistorySavePath
```

By default this is `$env:APPDATA\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt`. Every command you run gets appended. The file persists across sessions and reboots, so up-arrow recalls work after closing the shell.

This is also a forensic artifact, which we cover in detail in Chapter 11. For now, knowing where it lives matters because attackers sometimes try to clear or redirect it.

### Configuring PSReadLine

```
Set-PSReadLineOption -PredictionSource History
Set-PSReadLineOption -PredictionViewStyle ListView
```

The first turns on inline prediction: as you type, PSReadLine offers a faded-text completion based on history. Press right arrow to accept it. Genuinely useful once you get used to it.

The ListView style shows multiple suggestions in a small dropdown.

## Modules

A module is a packaged collection of commands. *In PowerShell, a module is a unit of distribution: a folder containing related cmdlets, functions, and resources.* Modules let third parties add new commands.

```
Get-Module                              # currently loaded modules
Get-Module -ListAvailable | Select-Object -First 20    # all modules installed on the system
```

The modules that ship with Windows include `Microsoft.PowerShell.Management` (Get-Process, Get-Service, etc.), `Microsoft.PowerShell.Utility` (Select-Object, Sort-Object, etc.), `NetTCPIP` (Get-NetTCPConnection), `NetSecurity` (Defender Firewall cmdlets), and many others.

Some modules load on demand: when you reference a command from a module, PowerShell loads the module automatically. Other modules require explicit import:

```
Import-Module Microsoft.PowerShell.LocalAccounts
```

For modules from the broader PowerShell community, the standard repository is the PowerShell Gallery:

```
Find-Module PSWindowsUpdate
Install-Module PSWindowsUpdate -Scope CurrentUser
```

`Find-Module` searches the gallery. `Install-Module` downloads and installs. `-Scope CurrentUser` installs for just your user without requiring admin (the alternative `AllUsers` requires elevation).

For this chapter, recognition is enough. You will install a module from the gallery later in the unit. The pattern is the same regardless of which module.

## Working with files

You have used `Get-ChildItem` to list directories. The full file-handling toolkit is broader.

### Reading text files

```
Get-Content C:\Windows\System32\drivers\etc\hosts
Get-Content -Tail 10 C:\Windows\System32\drivers\etc\hosts
Get-Content -TotalCount 5 C:\Windows\System32\drivers\etc\hosts
```

The first reads the whole file. The second is the last 10 lines (equivalent to `tail` on Linux). The third is the first 5 lines (`head`).

For following a file as it grows:

```
Get-Content -Wait -Tail 10 C:\path\to\log.log
```

The `-Wait` flag makes it follow, like `tail -f` on Linux. Press Ctrl+C to stop.

### Writing text files

```
Set-Content -Path test.txt -Value "Hello"        # overwrite
Add-Content -Path test.txt -Value "World"        # append
"Hello" | Out-File -FilePath test.txt            # also overwrite
"World" | Out-File -FilePath test.txt -Append    # also append
```

`Set-Content` and `Add-Content` are the cmdlet versions. `Out-File` and the `>` and `>>` redirect operators are the more bash-like versions. They do roughly the same thing with slightly different defaults around encoding.

Speaking of encoding: by default in PowerShell 5.1, file output is UTF-16 with a BOM. This trips up tools that expect UTF-8. Force UTF-8:

```
"Hello" | Out-File -FilePath test.txt -Encoding utf8
Set-Content -Path test.txt -Value "Hello" -Encoding utf8
```

In PowerShell 7+, the default encoding is UTF-8, which is friendlier. Worth knowing about both because you will work with both versions in your career.

### Searching inside files

`Select-String` is the PowerShell equivalent of grep:

```
Select-String -Path C:\Windows\System32\drivers\etc\hosts -Pattern "localhost"
Select-String -Path *.txt -Pattern "TODO" -SimpleMatch
ls C:\path -Recurse -Include *.log | Select-String -Pattern "ERROR"
```

`-SimpleMatch` does literal string matching (no regex). Without it, the pattern is treated as a regex. The output includes filename, line number, and the matching line, which is more structured than what `grep` returns.

## Editing files: notepad, notepad++, ISE, and VSCode

The Linux unit had a vi survival section. Windows has multiple editor options, none of which require survival skills the way vi does, but a few are worth knowing.

**`notepad`** is built into Windows. It is fine for simple edits. It is bad for large files, no syntax highlighting, no search-and-replace beyond basic. Suitable for one-off config edits, not for daily work.

```
notepad C:\path\to\file.txt
notepad $PROFILE
```

**`Notepad++`** is the de facto enthusiast editor on Windows. Free, fast, syntax-aware, supports many file formats. Install via winget:

```
winget install Notepad++.Notepad++
```

Once installed, `notepad++ <file>` works from PowerShell.

**`PowerShell ISE`** is the Integrated Scripting Environment that ships with Windows PowerShell 5.1. It has a script editor pane, a console pane, and command help. It is being deprecated in favor of VSCode, but it is on every Windows install and is genuinely useful for quick PowerShell editing without installing anything.

```
ise $PROFILE
```

**`VSCode`** with the PowerShell extension is the modern editor for serious PowerShell work. Install via winget:

```
winget install Microsoft.VisualStudioCode
```

Then install the PowerShell extension from inside VSCode. This is what most working admins use today for any PowerShell longer than a few lines.

For this unit's exercises, any of these works. Pick one and use it consistently. My recommendation: notepad for one-line tweaks, Notepad++ or VSCode for everything else.

## Parameters and parameter binding

Every cmdlet has parameters. The mechanics of how PowerShell decides which parameter gets your value is more sophisticated than bash's positional arguments.

### Named and positional

```
Get-Process -Name explorer
Get-Process explorer                    # positional; -Name is the first positional
```

Both work. The positional form depends on the parameter being marked as positional in its definition. Most common parameters have a position; less common ones require the explicit name.

### Switch parameters

Switches do not take a value; their presence is the value:

```
Get-ChildItem -Recurse
Get-ChildItem -Recurse -Force
```

`-Recurse` and `-Force` are switches. You either include them or you do not.

### Parameter aliases

Many parameters have shorter aliases:

```
ls -re                    # -Recurse can be abbreviated
Get-Help -? Get-Process   # -? is an alias for help
```

PowerShell accepts any unambiguous prefix of a parameter name. `-Re` works because no other parameter on `Get-ChildItem` starts with `Re`. Use full names in scripts; abbreviations are fine for interactive use.

### Pipeline binding

This is the part that distinguishes PowerShell from bash.

```
"explorer", "svchost" | Get-Process
```

That works because `Get-Process -Name` accepts pipeline input. PowerShell binds the strings flowing through the pipeline to the `-Name` parameter automatically.

The decision logic: PowerShell looks at the type of the incoming object and tries to match it to a parameter that accepts pipeline input. If multiple parameters could accept it, PowerShell tries "ByValue" first (just the type), then "ByPropertyName" (matching the parameter name to a property on the incoming object).

To see which parameters accept pipeline input:

```
Get-Help Get-Process -Parameter Name
```

Look for the "Accept pipeline input?" line. If it says "true (ByValue, ByPropertyName)", values flowing through the pipeline can bind to that parameter.

### A practical example

```
Get-Service | Where-Object Status -eq Stopped | Select-Object -First 3 | Get-Member
```

The pipeline carries `Service` objects through. `Where-Object` keeps the ones with `Status -eq Stopped`. `Select-Object -First 3` takes the first three. `Get-Member` shows what those objects are. The whole chain works because each cmdlet declares what it accepts via its parameter definitions.

When something does not bind the way you expect, `Get-Help <cmdlet> -Parameter *` shows the binding rules for every parameter.

## Error handling

Bash has `set -e`. PowerShell has `$ErrorActionPreference` and try/catch.

### Terminating versus non-terminating errors

PowerShell has two kinds of errors. *Terminating errors stop the script. Non-terminating errors are logged but the script continues.* By default, most errors are non-terminating, which means a script that hits a problem keeps going, often producing wrong output silently.

To make all errors terminating:

```
$ErrorActionPreference = 'Stop'
```

That is the equivalent of `set -e` in bash. Put it at the top of any script that matters.

For per-command override:

```
Get-Item C:\does-not-exist -ErrorAction Stop
Get-Item C:\does-not-exist -ErrorAction SilentlyContinue
```

`-ErrorAction Stop` makes that one cmdlet's error terminating. `SilentlyContinue` suppresses the error message entirely (use carefully; you are throwing away information).

### try/catch

Once errors are terminating, try/catch works:

```powershell
try {
    Get-Item C:\does-not-exist -ErrorAction Stop
}
catch {
    Write-Warning "File not found: $_"
}
```

The `$_` (or equivalently `$PSItem`) inside the catch block is the error record. It has properties: `Exception`, `Message`, `CategoryInfo`, `FullyQualifiedErrorId`, etc.

For more specific catches:

```powershell
try {
    $content = Get-Content C:\does-not-exist -ErrorAction Stop
}
catch [System.IO.FileNotFoundException] {
    Write-Warning "File missing"
}
catch [System.UnauthorizedAccessException] {
    Write-Warning "Permission denied"
}
catch {
    Write-Warning "Some other error: $_"
}
```

The exception types are .NET types. The pattern matches the most specific type first; catch-all is last.

### A finally block

```powershell
try {
    # do work
}
catch {
    Write-Warning "Failed: $_"
}
finally {
    # cleanup that runs whether or not the try succeeded
}
```

`finally` is the cleanup hook. It runs whether the try succeeded or threw. Use it for closing files, releasing locks, undoing temporary changes.

## A few execution-environment things worth knowing

### Execution policy revisited

The workshop touched on this. Worth knowing the full set of values:

- `Restricted`: no scripts run. Default on some systems.
- `AllSigned`: only scripts signed by a trusted publisher run.
- `RemoteSigned`: local scripts run unconditionally; downloaded scripts must be signed.
- `Unrestricted`: any script runs, with a prompt for downloaded ones.
- `Bypass`: any script runs, no prompts. Used in tooling.

```
Get-ExecutionPolicy
Get-ExecutionPolicy -List
```

The List form shows the policy at every scope: machine, user, process. The effective policy is the most restrictive.

For development on your own machine: `RemoteSigned` at `CurrentUser` scope is the right default.

### Constrained Language Mode

A brief mention. *Constrained Language Mode (CLM) is a PowerShell mode that disables most language features, used in environments with WDAC or Device Guard policies.* When CLM is on, you cannot define classes, you cannot use most .NET types, you cannot use add-type. Many scripts written for normal PowerShell will fail.

Check whether you are in CLM:

```
$ExecutionContext.SessionState.LanguageMode
```

`FullLanguage` is normal. `ConstrainedLanguage` is CLM. On a typical lab box this returns `FullLanguage`; CLM is something you see in tightly managed corporate environments. Knowing it exists matters because some PowerShell techniques you learn will not work everywhere.

### AMSI

*AMSI, the Antimalware Scan Interface, is a Windows feature that lets antivirus tools scan the contents of a script before it executes.* Modern Defender hooks PowerShell through AMSI, which means the actual contents of scripts are scanned, not just the file on disk.

For most working admins, AMSI is invisible. For security pros, AMSI is what catches obfuscated PowerShell payloads at runtime. Adversary techniques that try to bypass AMSI are a real category of attack. We touch this lightly in Chapter 9.

## Try this

**1. Set up your profile.**

Create `$PROFILE` if it does not exist. Add at minimum:

- A custom prompt that includes the time.
- The `$ErrorActionPreference = 'Stop'` line (so your interactive shell fails loud, like a script would).
- A useful alias, like `Set-Alias ll Get-ChildItem`.
- The PSReadLine prediction config: `Set-PSReadLineOption -PredictionSource History`.

Restart PowerShell. Confirm the changes took effect.

**2. Explore one parameter binding.**

Run:

```
Get-Help Get-Process -Parameter Name
Get-Help Get-Process -Parameter Id
```

For each, identify whether it accepts pipeline input, and how (ByValue, ByPropertyName, both, neither). Then test:

```
"explorer" | Get-Process
1234 | Get-Process
[PSCustomObject]@{Name='explorer'} | Get-Process
[PSCustomObject]@{Id=1234} | Get-Process
```

Notice which ones work and why. The first two work because the type matches the parameter's expected type for ByValue binding. The third and fourth work because the property name matches.

**3. Read your PowerShell history.**

```
Get-PSReadLineOption | Select-Object HistorySavePath
notepad (Get-PSReadLineOption).HistorySavePath
```

Read your history. It contains every PowerShell command you have run, across every session, since the file was created. This is one of the artifacts a security analyst would collect first.

**4. Write a simple try/catch script.**

Save the following as `try-test.ps1`:

```powershell
$ErrorActionPreference = 'Stop'

try {
    $size = (Get-Item C:\Windows\System32\notepad.exe).Length
    Write-Host "notepad.exe size: $size bytes"
    
    # This should fail
    $missing = Get-Item C:\does-not-exist
}
catch {
    Write-Warning "Caught error: $($_.Exception.Message)"
}
finally {
    Write-Host "Done."
}
```

Run it. Confirm:
- The first Get-Item succeeds and prints the size.
- The second fails and is caught.
- The finally block runs.

**5. Explore one module from the Gallery.**

Run:

```
Find-Module -Name PSWindowsUpdate
Get-Module -ListAvailable -Name PSWindowsUpdate
```

If the module is not installed, install it for your user:

```
Install-Module PSWindowsUpdate -Scope CurrentUser -Force
```

Then explore what it adds:

```
Import-Module PSWindowsUpdate
Get-Command -Module PSWindowsUpdate
Get-Help Get-WindowsUpdate
```

You do not need to actually run any updates. The exercise is the round-trip: find a module, install it, see what commands it adds, read help for one of them. This is the workflow for adding any third-party functionality to your PowerShell.

## Common stumbling blocks

> **My profile changes do not take effect.**
> Either you saved to the wrong file (confirm `$PROFILE` returns the path you edited), or you have not restarted PowerShell or dot-sourced the profile (`. $PROFILE` from the current session).

> **A script that worked on PowerShell 7 fails on Windows PowerShell 5.1.**
> 5.1 is missing many language features added in 7+: ternary operators, pipeline chain operators (`&&` and `||`), some method overloads. Check your script's `#Requires -Version` directive. For Windows servers, defaulting to writing for 5.1 is the safe choice because that is what is on every box.

> **`Install-Module` fails with "Untrusted repository."**
> The first time you install from PSGallery, PowerShell asks for confirmation. Either accept the prompt, or trust the gallery once: `Set-PSRepository -Name PSGallery -InstallationPolicy Trusted`.

> **Tab completion stops working in the middle of a session.**
> PSReadLine sometimes loses its state, especially after long-running commands. Try pressing Ctrl+C to abort the current input, then try Tab again. If that does not work, restart the shell.

> **My script throws "is not recognized as a cmdlet" but the command works in my interactive session.**
> The interactive session has your profile loaded; the script does not (by default). If the command comes from a module, your profile may be importing it implicitly. Add explicit `Import-Module <name>` at the top of the script.

> **Out-File or > redirect created a file that other tools cannot read.**
> Encoding. Windows PowerShell 5.1 defaults to UTF-16 with BOM, which many tools cannot parse. Use `-Encoding utf8` (or `Set-Content` which has cleaner defaults), or upgrade to PowerShell 7+ where UTF-8 is the default.

> **My try/catch does not catch a Get-* command's error.**
> Most cmdlet errors are non-terminating by default. Add `-ErrorAction Stop` to make the specific cmdlet's error terminating, or set `$ErrorActionPreference = 'Stop'` for the whole script.

After this chapter:

- You have a customized PowerShell environment with a profile, a useful prompt, and good defaults.
- You know how the help system works and can read parameter help fluently.
- You understand the pipeline as object streams, with binding rules you can predict.
